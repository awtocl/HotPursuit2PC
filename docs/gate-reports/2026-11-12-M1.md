# Gate Report — 2026-11-12 — Milestone 1 (Running & Stable)

Type: **milestone gate** — stop for the owner to try the game (brief §7, §10).

**Which path shipped (brief §5): Path C — emulator-backed.** The PS2 game code
from the owner's disc runs inside the open-source Play! core, linked into our
launcher. It is the PS2 game (not the 2003 PC port), with our window, input,
audio output and file layout around it. **It is not a native Windows port.**
What that means for fidelity: game logic is the original code, so handling,
AI, cameras and menus are the PS2 game's; rendering, sound and timing are as
accurate as the Play! core is for this game — good in everything checked so
far, but only partly checked (see §3).

## 1. What changed / why

| Phase | Commit | What |
|---|---|---|
| P4b M1 runtime | `aa10b4f` | Owner approved fetching Play! (Q1). `engine/`: launcher `HotPursuit2.exe` on Play! `1f27232` (source unmodified, BSD-2); virtual disc that serves `game/rom` to the core without an image file; converter stage `build` (the launcher travels inside the converter); ADR 0005; license notices for all ten linked third-party components. |
| P5 M1 evidence | this commit | Acceptance runs written up in `docs/evidence/m1-acceptance.md`; this report. |

Key decisions (ADR 0005): link the core's libraries directly instead of using
its libretro wrapper (keeps every written file inside the game folder);
OpenGL renderer at 2× internal resolution by default; the core's 60 Hz limiter
stays on; nothing in the game's own pacing is altered.

A finding that needs the owner's attention: **the game draws races at 30
frames per second and menus at 60.** Five experiments giving the game a
faster emulated CPU left the race at 30, so this is the game's own choice,
not a performance limit — but it has not been confirmed on a real console.
The brief's C7 ("60 fps baseline") is met in the sense that the console's
60 Hz timing and the game's speed are preserved exactly; it is *not* met if
the owner's expectation is 60 drawn frames per second during races.

## 3. Not verified

- **Nobody has played it.** Feel of the handling, audio quality by ear, lip-sync of movies, and visual correctness beyond a few dozen screenshots are unjudged. This is the main thing the gate is for.
- **30 vs 60 fps in races on the real console** — UNVERIFIED (see §1).
- **A clean Windows machine** — everything ran on one development PC. Other GPUs and drivers are untested.
- **Length and breadth:** one 2.5-minute session, Quick Race on one track. No completed race, no You're The Cop / Championship / World Racing, no split-screen, no long session.
- **Controller:** XInput path exercised only through the same code as the scripted input; no physical pad was used. DualShock 2 button pressure is not emulated; rumble is not implemented.
- **Rear-view mirror:** a striped band at its lower edge in screenshots — unknown whether original.
- **GitHub Actions** has still never run (nothing pushed). It now also has to fetch Play!.
- Audio output averaged 43.3 kHz of the nominal 44.1 kHz because of the loading-time dips; whether that is audible is unjudged.
- 40 unnamed asset files, IRX set selection, internal asset formats: unchanged from the previous report.

## 5. What the owner needs to do

1. **Play it:** start `.cache\m1-run\game\build\HotPursuit2.exe`. Xbox-style pad or keyboard (arrows, X = Cross, Enter = Start; full list in `README.txt`); Alt+Enter for full screen.
2. Judge the things only a person can (STATUS Q6–Q8): does it feel like the PS2 game; were races 30 or 60 fps on your console; is the sound clean; does throttle/brake need analog pressure.
3. Optionally try the whole flow: copy `HotPursuit2PC.exe` to an empty folder, run it, pick the ROM folder.
4. Decide Q3 (MIT license) and whether to push — nothing has been pushed.
5. Disk space: about 25 GB of evidence scratch sits in `.cache\` (list in STATUS); nothing was deleted.

## 6. Next phase plan (after approval of Milestone 1)

Milestone 2, each feature with its own ADR, opt-in where it changes the original:

1. **Anti-aliasing / upscaling first.** With this core the honest options are higher internal resolution (already available, `--res`), supersampling, and post-process AA; a true DLAA needs motion vectors the PS2 pipeline does not produce — to be laid out in the ADR rather than promised.
2. Resolution/aspect (widescreen), save robustness (save states), a config file and in-launcher settings, controller improvements (rumble, pressure, remapping), frame-rate modes — including, if wanted, a 60 fps race mode as an opt-in patch.
3. Native track in parallel (ADR 0001 stages N1/N2), starting with Play!'s ahead-of-time block cache options.

If the owner's verdict is that fidelity is off (handling, timing, sound), that
comes first: diagnose against the core, or reopen ADR 0001/0005.
